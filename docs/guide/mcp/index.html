Open-source guide

Connect your agent over MCP

Register the local Drizza MCP endpoint in Claude Code or Codex, and let your agent push the daily briefing to the dashboard.

How it works

Drizza never calls a model. Your own agent (Claude Code or Codex) reads your day with the access it already has, writes the briefing, and pushes it to Drizza through a local MCP endpoint. The Briefing de hoje card updates by itself a few seconds after the push.

  • The endpoint is http://127.0.0.1:4340/mcp, on the same loopback server as the dashboard. It follows the port you pass with --port.
  • It speaks MCP over Streamable HTTP: every message is a POST to /mcp. GET and other methods get 405.
  • Every POST needs the local token as a Bearer token in the Authorization header.

Start Drizza and load the token

Start Drizza as described in Run locally:

npx drizza

On the first start, Drizza creates a random token and stores it in ~/.drizza/mcp-token, readable only by your user. The token file always sits next to the database, so with --db <path> it lives in the same directory as that database. Drizza never prints the token.

After it starts, Drizza prints the endpoint, where the token is, and the registration commands for both agents. Those lines are in Brazilian Portuguese, and they carry the absolute path of your token file and the port in use. With the defaults, they match the commands on this page.

In the shell that will open Claude Code or Codex, load the token into a variable:

export DRIZZA_MCP_TOKEN=$(cat ~/.drizza/mcp-token)

The agents keep only a reference to DRIZZA_MCP_TOKEN in their configuration and read its value when they connect. Export it in every shell that opens the agent, for example from your shell profile.

Keep the token out of the command line. Do not register with --header "Authorization: Bearer $(cat ...)". The token would show up in the process list and could be stored in plain text in the agent configuration.

Register in Claude Code

claude mcp add --transport http drizza http://127.0.0.1:4340/mcp --header 'Authorization: Bearer ${DRIZZA_MCP_TOKEN}'

Keep the single quotes: they make Claude Code store the reference ${DRIZZA_MCP_TOKEN}, not the token. Claude Code reads the variable each time it connects.

By default, claude mcp add registers the server only for the directory you run it in. To make Drizza available in every project, add --scope user:

claude mcp add --scope user --transport http drizza http://127.0.0.1:4340/mcp --header 'Authorization: Bearer ${DRIZZA_MCP_TOKEN}'

Check the connection with Drizza running:

claude mcp list

The drizza line should say Connected. The tools show up in Claude Code as mcp__drizza__get_today, mcp__drizza__push_briefing and mcp__drizza__push_items.

Register in Codex

codex mcp add drizza --url http://127.0.0.1:4340/mcp --bearer-token-env-var DRIZZA_MCP_TOKEN

Codex stores the server in ~/.codex/config.toml with the name of the variable, not its value:

[mcp_servers.drizza]
url = "http://127.0.0.1:4340/mcp"
bearer_token_env_var = "DRIZZA_MCP_TOKEN"

Check the registration:

codex mcp get drizza

This shows the stored configuration; it does not test the connection.

Running Codex non-interactively

In codex exec, nobody is there to approve tool calls, so Codex blocks the calls to the Drizza tools and the briefing is not pushed. To allow them, add this line under [mcp_servers.drizza] in ~/.codex/config.toml:

default_tools_approval_mode = "approve"

This approves every Drizza tool without asking, in interactive sessions too. Leave it out if you prefer to approve each call.

Run the briefing skill

Drizza ships a skill, skills/drizza-briefing/SKILL.md in the package and in the repository, that teaches both agents to build the briefing. It reads what Drizza already has with get_today, collects the day from sources the agent can already reach (GitHub through gh, plus Slack, Linear or others only if the agent already has a tool for them), and pushes the result with push_briefing. The agent never reads the token file or the database.

Download the skill into each agent's skills folder:

mkdir -p ~/.claude/skills/drizza-briefing && curl -fsSL https://raw.githubusercontent.com/drizza-dev/drizza/main/skills/drizza-briefing/SKILL.md -o ~/.claude/skills/drizza-briefing/SKILL.md
mkdir -p ~/.codex/skills/drizza-briefing && curl -fsSL https://raw.githubusercontent.com/drizza-dev/drizza/main/skills/drizza-briefing/SKILL.md -o ~/.codex/skills/drizza-briefing/SKILL.md

Then run it in Claude Code:

/drizza-briefing

Or in Codex:

$drizza-briefing

The Copiar comando do briefing button in the dashboard copies the Claude Code command. When the agent finishes, the briefing shows up in the Briefing de hoje card with links to its sources.

Tools

The tools follow contract version 1. Every call sends "contract_version": "1". Inputs are closed: a field the contract does not define is rejected. Drizza reports its contract version in the _meta of the initialize (or server/discover) response, under dev.drizza/contract_version; a client should check it before sending a field from a newer contract. A call that fails validation returns a tool error with the path of each invalid field, so the agent can fix the payload and try again.

get_today

Reads what Drizza has for a day. Send only contract_version to read today, or add date as YYYY-MM-DD. Without date, today is the local date of the machine running Drizza, not UTC.

{ "contract_version": "1" }

It returns date, briefing (the stored briefing, or null) and items. items lists only what an agent pushed or enriched through push_items on that local day, newest first, up to 200. A GitHub sync alone never puts an item there.

Each item in items has source, kind, external_id, origin (agent for items you pushed, sync for synced pull requests you enriched), title and received_at (when Drizza last stored it). url, summary and updated_at appear only when they have a value.

push_briefing

Stores the briefing for one day. A second push for the same date replaces the previous one, and the response says so with replaced.

  • date (YYYY-MM-DD), agent (1 to 64 characters), headline (1 to 200) and sections (1 to 12) are required.
  • Each section has a title (1 to 120 characters) and 1 to 30 bullets. Each bullet has a text (1 to 1000) and optional links (up to 10) and item_refs (up to 10).
  • A link has exactly url, label and source (github, slack or other). The URL must be an absolute http:// or https:// address without a username or password. Drizza stores it normalized, and the normalized URL must still fit in 2048 characters.
  • An item_ref points at an item by the same source and external_id used in push_items. When source is exactly github, the external_id is lowercased, as in push_items, so the reference matches the item that get_today returns.

It returns briefing_id, date and replaced.

push_items

Stores items such as threads or pull requests: items holds 1 to 100 of them per call. Each item has:

  • source (required, 1 to 32 characters), for example github or slack.
  • kind (required, 1 to 32 characters), for example pull_request or thread.
  • external_id (required, 1 to 256 characters), the identifier of the item inside its source.
  • title (required, 1 to 300 characters).
  • url (optional, an absolute http:// or https:// URL of up to 2048 characters).
  • summary (optional, 1 to 2000 characters), your short summary.
  • updated_at (optional), when the item last changed in its source, as an RFC 3339 timestamp.

No other field is accepted. How Drizza stores them:

  • Upsert that merges. Items are matched by source and external_id. Pushing an existing key updates it, and an optional field you leave out keeps its stored value. Clearing a field is not supported yet.
  • Case of the key. source is case sensitive. Only when it is exactly github is the external_id matched without regard to case (it is stored lowercased), for any kind. GitHub or any other casing is a separate source.
  • GitHub pull requests. Pull requests synced from GitHub use source github, kind pull_request and external_id owner/repo#number. Pushing that key adds your summary to the synced pull request and keeps its title, URL, kind and update time as synced.
  • Adopted by the sync. If the GitHub sync later reports an item you pushed under that key, it takes it over: kind, title, URL and update time are replaced with the synced values, and your summary is kept.
  • Kept after the sync. If a pull request you enriched or pushed leaves the GitHub sync, Drizza keeps it as your item, with your summary.
  • Safe URLs. A URL with a username or password is rejected. Stored URLs are normalized, and the normalized URL must still fit in 2048 characters.

It returns inserted and updated, which add up to the number of items you pushed.

Find, rotate, or revoke the token

The token is in ~/.drizza/mcp-token, or next to the database you pass with --db. Drizza refuses to start if the file can be read by other users; fix it with chmod 600 or delete it to get a new one.

To rotate the token:

  1. Stop Drizza.
  2. Delete the token file: 
    rm ~/.drizza/mcp-token
  3. Start Drizza again. It creates a new token, and the old one stops working.
  4. Load the new token in the shell that opens the agent: 
    export DRIZZA_MCP_TOKEN=$(cat ~/.drizza/mcp-token)
  5. Restart Claude Code or Codex from that shell. You do not need to register the server again, since the agents store only the variable name.

Drizza reads the token file only when it starts, so the old token keeps working until Drizza restarts.

To remove Drizza from an agent, unregister the server:

claude mcp remove drizza
codex mcp remove drizza

Endpoint security

  • The endpoint shares the dashboard server, which binds to 127.0.0.1. Drizza checks each request to /mcp in this order:
    1. Host. A Host that is not the local Drizza address gets 403.
    2. Origin. The Origin header is optional, because command-line MCP clients do not send it. When it is present and is not the local Drizza address, Drizza answers 403, so a web page you open cannot call the endpoint from your browser.
    3. Method. Anything other than POST gets 405.
    4. Token. Every POST that passed the checks above needs the Bearer token. Without it, or with a wrong one, Drizza answers 401.
  • The token is never written to the database, logs, API responses, or the dashboard.

Troubleshooting

The agent cannot connect (401)

claude mcp list reports that the server rejected the Authorization header (HTTP 401), and may warn that DRIZZA_MCP_TOKEN is missing. Export the variable as shown above in the shell that opens the agent and restart it. If you rotated the token, export it again.

The tools are missing

Drizza must be running when the agent starts. Start Drizza, confirm the port matches the registered URL, and restart the agent. If you started Drizza with --port, register the URL it prints.

Codex does not push the briefing

In codex exec, add default_tools_approval_mode = "approve" as described in Running Codex non-interactively.
