Conectar seu agente por MCP

Registre o endpoint MCP local do Drizza no Claude Code ou no Codex e deixe seu agente enviar o briefing do dia para o dashboard.

Como funciona

O Drizza nunca chama um modelo. O seu próprio agente (Claude Code ou Codex) lê o seu dia com os acessos que já tem, escreve o briefing e o envia ao Drizza por um endpoint MCP local. O card Briefing de hoje se atualiza sozinho alguns segundos depois do envio.

  • O endpoint é http://127.0.0.1:4340/mcp, no mesmo servidor de loopback do dashboard. Ele segue a porta passada em --port.
  • Ele fala MCP sobre Streamable HTTP: toda mensagem é um POST em /mcp. GET e os outros métodos recebem 405.
  • Toda requisição precisa do token local como token Bearer no header Authorization.

Iniciar o Drizza e carregar o token

Inicie o Drizza como descrito em Rodar localmente:

node dist-node/cli/index.js

Na primeira vez, o Drizza cria um token aleatório e o guarda em ~/.drizza/mcp-token, legível só pelo seu usuário. O arquivo do token fica sempre ao lado do banco: com --db <caminho>, ele fica no mesmo diretório desse banco. O Drizza nunca exibe o token.

Depois de subir, o Drizza imprime o endpoint, onde está o token e os comandos de registro dos dois agentes, já com o caminho absoluto do seu arquivo de token e a porta em uso. Com os valores padrão, eles batem com os comandos desta página.

No shell que vai abrir o Claude Code ou o Codex, carregue o token numa variável:

export DRIZZA_MCP_TOKEN=$(cat ~/.drizza/mcp-token)

Os agentes guardam na configuração só uma referência a DRIZZA_MCP_TOKEN e leem o valor quando se conectam. Exporte a variável em todo shell que abre o agente, por exemplo pelo perfil do seu shell.

Mantenha o token fora da linha de comando. Não registre com --header "Authorization: Bearer $(cat ...)". O token apareceria na lista de processos e poderia ficar em texto puro na configuração do agente.

Registrar no Claude Code

claude mcp add --transport http drizza http://127.0.0.1:4340/mcp --header 'Authorization: Bearer ${DRIZZA_MCP_TOKEN}'

Mantenha as aspas simples: com elas, o Claude Code guarda a referência ${DRIZZA_MCP_TOKEN}, não o token. Ele lê a variável a cada conexão.

Por padrão, claude mcp add registra o servidor só para o diretório em que você roda o comando. Para deixar o Drizza disponível em todos os projetos, acrescente --scope user:

claude mcp add --scope user --transport http drizza http://127.0.0.1:4340/mcp --header 'Authorization: Bearer ${DRIZZA_MCP_TOKEN}'

Com o Drizza rodando, confira a conexão:

claude mcp list

A linha do drizza deve dizer Connected. As tools aparecem no Claude Code como mcp__drizza__get_today, mcp__drizza__push_briefing e mcp__drizza__push_items.

Registrar no Codex

codex mcp add drizza --url http://127.0.0.1:4340/mcp --bearer-token-env-var DRIZZA_MCP_TOKEN

O Codex guarda o servidor em ~/.codex/config.toml com o nome da variável, não o valor:

[mcp_servers.drizza]
url = "http://127.0.0.1:4340/mcp"
bearer_token_env_var = "DRIZZA_MCP_TOKEN"

Confira o registro:

codex mcp get drizza

Isso mostra a configuração guardada; não testa a conexão.

Rodar o Codex em modo não interativo

No codex exec, não há ninguém para aprovar as chamadas de tools, então o Codex bloqueia as chamadas às tools do Drizza e o briefing não é enviado. Para liberá-las, acrescente esta linha em [mcp_servers.drizza] no ~/.codex/config.toml:

default_tools_approval_mode = "approve"

Isso aprova todas as tools do Drizza sem perguntar, também nas sessões interativas. Deixe de fora se preferir aprovar cada chamada.

Rodar o skill de briefing

O repositório traz um skill, skills/drizza-briefing/SKILL.md, que ensina os dois agentes a montar o briefing. Ele lê o que o Drizza já tem com get_today, coleta o dia nas fontes que o agente já alcança (GitHub pelo gh, e Slack, Linear ou outras só se o agente já tiver uma ferramenta para elas) e envia o resultado com push_briefing. O agente nunca lê o arquivo do token nem o banco.

A partir da raiz do seu clone, copie o skill para a pasta de skills de cada agente:

mkdir -p ~/.claude/skills/drizza-briefing && cp skills/drizza-briefing/SKILL.md ~/.claude/skills/drizza-briefing/
mkdir -p ~/.codex/skills/drizza-briefing && cp skills/drizza-briefing/SKILL.md ~/.codex/skills/drizza-briefing/

Depois rode no Claude Code:

/drizza-briefing

Ou no Codex:

$drizza-briefing

O botão Copiar comando do briefing do dashboard copia o comando do Claude Code. Quando o agente termina, o briefing aparece no card Briefing de hoje com links para as fontes.

Tools

As tools seguem a versão 1 do contrato. Toda chamada envia "contract_version": "1". As entradas são fechadas: campo que o contrato não define é recusado. O Drizza informa a versão do contrato no _meta da resposta do initialize (ou do server/discover), na chave dev.drizza/contract_version; o cliente deve conferi-la antes de enviar um campo de um contrato mais novo. Uma chamada que falha na validação devolve um erro da tool com o caminho de cada campo inválido, para o agente corrigir o payload e tentar de novo.

get_today

Lê o que o Drizza tem para um dia. Envie só contract_version para ler hoje, ou acrescente date como YYYY-MM-DD. Sem date, hoje é a data local da máquina que roda o Drizza, não UTC.

{ "contract_version": "1" }

Devolve date, briefing (o briefing guardado, ou null) e items. items lista só o que um agente enviou ou enriqueceu por push_items naquele dia local, do mais recente ao mais antigo, até 200. Um sync do GitHub sozinho nunca coloca um item ali.

push_briefing

Guarda o briefing de um dia. Um segundo envio para a mesma date substitui o anterior, e a resposta indica isso em replaced.

  • date (YYYY-MM-DD), agent (1 a 64 caracteres), headline (1 a 200) e sections (1 a 12) são obrigatórios.
  • Cada seção tem um title (1 a 120 caracteres) e de 1 a 30 bullets. Cada bullet tem um text (1 a 1000) e, opcionalmente, links (até 10) e item_refs (até 10).
  • Um link tem exatamente url, label e source (github, slack ou other). A URL precisa ser um endereço absoluto http:// ou https:// sem usuário nem senha. O Drizza a guarda normalizada, e a URL normalizada ainda precisa caber em 2048 caracteres.
  • Um item_ref aponta para um item pelos mesmos source e external_id usados em push_items. Quando o source é exatamente github, o external_id é convertido para minúsculas, como em push_items, para a referência casar com o item que o get_today devolve.

Devolve briefing_id, date e replaced.

push_items

Guarda até 100 itens por chamada, como conversas ou pull requests. Cada item precisa de source, kind, external_id e title, e pode trazer url, summary e updated_at (um timestamp RFC 3339).

  • Upsert que mescla. Os itens são casados por source e external_id. Enviar uma chave que já existe atualiza o item, e um campo opcional que você omite mantém o valor guardado. Ainda não dá para limpar um campo.
  • Maiúsculas na chave. O source diferencia maiúsculas de minúsculas. Só quando ele é exatamente github o external_id é casado sem diferenciar maiúsculas (e guardado em minúsculas), para qualquer kind. GitHub ou qualquer outra grafia é outra fonte.
  • Pull requests do GitHub. Pull requests sincronizadas do GitHub usam source github, kind pull_request e external_id owner/repo#number. Enviar essa chave acrescenta o seu summary à pull request sincronizada e mantém título, URL, tipo e data de atualização como vieram do sync.
  • Adotado pelo sync. Se o sync do GitHub depois trouxer um item que você enviou com essa chave, ele assume o item: tipo, título, URL e data de atualização passam a ser os do sync, e o seu resumo é mantido.
  • Mantido depois do sync. Se uma pull request que você enriqueceu ou enviou sai do sync do GitHub, o Drizza a mantém como item seu, com o seu resumo.
  • URLs seguras. URL com usuário ou senha é recusada. As URLs guardadas são normalizadas, e a URL normalizada ainda precisa caber em 2048 caracteres.

Devolve inserted e updated, que somam o número de itens enviados.

Achar, rotacionar ou revogar o token

O token fica em ~/.drizza/mcp-token, ou ao lado do banco passado em --db. O Drizza se recusa a subir se o arquivo puder ser lido por outros usuários; corrija com chmod 600 ou apague o arquivo para gerar outro.

Para rotacionar o token:

  1. Pare o Drizza.
  2. Apague o arquivo do token: 
    rm ~/.drizza/mcp-token
  3. Inicie o Drizza de novo. Ele cria um token novo, e o antigo para de funcionar.
  4. Carregue o token novo no shell que abre o agente: 
    export DRIZZA_MCP_TOKEN=$(cat ~/.drizza/mcp-token)
  5. Reinicie o Claude Code ou o Codex a partir desse shell. Não é preciso registrar o servidor de novo, porque os agentes guardam só o nome da variável.

O Drizza lê o arquivo do token só ao subir, então o token antigo continua valendo até o Drizza reiniciar.

Para tirar o Drizza de um agente, remova o registro do servidor:

claude mcp remove drizza
codex mcp remove drizza

Segurança do endpoint

  • O endpoint divide o servidor com o dashboard, que escuta só em 127.0.0.1 e recusa requisições cujo Host não é o endereço local.
  • O token Bearer é obrigatório em toda requisição. Sem ele, ou com um token errado, o Drizza responde 401.
  • O header Origin é opcional, porque clientes MCP de linha de comando não o enviam. Quando presente e diferente do endereço local do Drizza, a resposta é 403, então uma página web aberta no seu browser não consegue chamar o endpoint.
  • O token nunca é gravado no banco, em logs, em respostas da API nem no dashboard.

Solução de problemas

O agente não conecta (401)

O claude mcp list informa que o servidor recusou o header Authorization (HTTP 401) e pode avisar que DRIZZA_MCP_TOKEN está faltando. Exporte a variável como mostrado acima no shell que abre o agente e reinicie-o. Se você rotacionou o token, exporte de novo.

As tools não aparecem

O Drizza precisa estar rodando quando o agente sobe. Inicie o Drizza, confira se a porta bate com a URL registrada e reinicie o agente. Se você iniciou o Drizza com --port, registre a URL que ele imprime.

O Codex não envia o briefing

No codex exec, acrescente default_tools_approval_mode = "approve" como descrito em Rodar o Codex em modo não interativo.
